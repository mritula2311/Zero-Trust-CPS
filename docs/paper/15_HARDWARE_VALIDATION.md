The preserved MPU held-out evaluation ran [evaluate_real_hardware.py](../../scripts/evaluate_real_hardware.py) on TEST session 20260902_221217 using the then-current IF/LSTM/GCN/fusion artifacts. `evaluate_real_hardware.py` now requires an explicit `--relational-model {gcn,m6_deployed,m6_corrected}` pin (`src/relational_pin.py`) rather than reading ambient config, so a rerun no longer silently mixes lineages. It selects no threshold on TEST. Its warm-up rule excludes the first two temporal windows after relevant resets, leaving 42 scored readings from 116 raw rows. At-rest false alarms are 5/12; physical disturbances detected are 30/30. Printed Wilson intervals and phase medians are in [13 Q](13_RESULTS_MASTER_TABLES.md) and the [fresh log](../../results/final_verification/hardware_evaluation.log).

This is the strongest directly reproduced physical component-chain evidence, but the 41.7% resting false-alarm rate prevents a low-false-alarm hardware claim. The actions are hand-induced motion/fault phases. No cyberattack was performed in this held-out physical replay; it does not measure authenticated attack prevention or final policy enforcement. M6 fusion's performance on this evidence IS now established (2026-09-07, `--relational-model m6_corrected`): identical to GCN — 30/30 detection, 5/12 resting FP, no regression — see [13](13_RESULTS_MASTER_TABLES.md) O4/O5 and `results/m6_corrected_policy/hardware_regression.json`.

## SW-420 boundary

The first SW capture is 20260905_162002: 321 labelled records, including 140 all-zero at-rest feature vectors, allocated to TRAIN. Network test metrics exclude its pending rows. Simulated SW-like nodes do not close this physical gap. Local four-channel checkpoints and passing schema tests prove software compatibility, not generalization.

**[UPDATED 2026-09-07 — held-out SW-420 evidence now exists, evaluated outside this audit's original GCN-era replay scope.]** Two independent physical held-out sessions were captured: `20260907_165627` (VALIDATION, 299 operator-marked records) and `20260907_170639` (TEST, 343 operator-marked records), same protocol as the MPU6050 sessions above. Scored through `scripts/evaluate_real_hardware.py --device esp32-vib-002`: VALIDATION 0/70 resting FP (Wilson 95% CI [0.0%, 5.2%]), 109/109 detection (CI [96.6%, 100%]); TEST 0/108 resting FP (CI [0.0%, 3.4%]), 115/115 detection (CI [96.8%, 100%]) — identical under both the `gcn` pin and the deployed `m6_corrected` pin. Full detail and the "read qualification, not a better-sensor claim" caveat (SW-420 is a binary switch — `trigger_rate` reads exactly 0 on a still desk by construction, a structurally easier discrimination problem than MPU6050's continuous-amplitude resting noise): `results/sw420_real_hardware/summary.md`.

This closure exposed and fixed a real evaluator bug: `evaluate_real_hardware.py` had its target device hardcoded, and once an SW-420 session entered the same split-allocation manifest as an MPU6050 session, the evaluator would have silently scored SW-420's `trigger_rate`-shaped readings through the MPU6050's Isolation Forest/LSTM-AE models — a feature-vector shape mismatch that would have corrupted the MPU6050 numbers reported earlier in this document. Fixed with an explicit `--device` argument and per-device row filtering; the MPU6050 numbers above were re-verified to reproduce byte-identically after the fix.

Two sessions remains a real minimum, not a large sample — the same caveat this document already applies to MPU6050's 5/12. No fault-injection, mounting-robustness, or coordinated (`--devices esp32-vib-001,esp32-vib-002`) SW-420 sessions exist yet.

SW-420 measures comparator-trigger activity rather than acceleration magnitude. A disconnected input, inappropriate potentiometer setting and still sensor can share an all-zero reading. Require a recorded functional tap check and comparator setting in subsequent capture metadata. Do not use the heterogeneous second sensor to infer MPU manufacturing generalization.
