How a message becomes a decision read this first

Every telemetry message walks this path in order. Anything that fails an authentication step is rejected outright and never reaches a model — and, critically, a rejected message never touches the claimed device's own trust state (it only increments an identity-targeting counter, so nobody can lower a device's score just by spamming its ID).
identity→ revoked?→ HMAC-SHA256→ replay (boot_id/seq)→ timestamp freshness ⇒any failure = REJECTED
SECURITY TRUST — rate, step-up, silence + PROCESS ANOMALY — rule + Isolation Forest + LSTM-AE + GNN → fusion → 2×2 policy lookup→ ALLOW / ALERT / STEP_UP / BLOCK
The two scores are computed from completely separate evidence and meet only at that final lookup — they are never averaged into one number. A device with valid credentials reporting a violently abnormal reading, and one with forged credentials reporting a perfectly normal reading, must produce different responses; a single blended score cannot tell them apart.

Two-Score Timeline — the separation, over time

The architecture's central claim is that these two scores never blend. A single number cannot show that; two lines can. Security Trust answers "are the papers real?" and Process Anomaly answers "is the machine behaving?" — so a physically disturbed but correctly-authenticated device should drop the violet line while the cyan one holds flat. Dashed rule is the 0.6 decision threshold; shaded bands mark spans where the two disagree, which is precisely where a blended score would have been wrong. Oldest on the left, newest on the right.

NIST SP 800-207

Governance completeness: the fraction of recent logged decisions that carry each tenet's tag. Every decision is tagged at the moment it is made, so this is measured evidence recomputed from the audit log — not a checklist someone ticked. The count after each bar is how many audit rows back it.

NIST SP 800-207 — Governance Validation

Coverage (left) measures whether a tenet was tagged. This measures whether the claim holds. It matters because tenets_for_decision() writes tenets 1/3/4/5/6 on every decision unconditionally — so 100% coverage for those is true by construction, not a finding. Each check below reads only the hash-chained audit log, never live process state, and states the observation that would falsify it. evaluate_governance.py injects each falsifier as synthetic rows and confirms 6/6 checks reject it, so these are not vacuous.

RL Policy — what the gateway would decide process bucket = 9

The deployed policy sliced at process bucket 9 (process score 0.9–1.0), one row per security-score bucket. The decision column is what this gateway would actually return for that state — read from the same object it uses live, so this table cannot drift from behaviour. Q-values are expected reward (+1 correct action, −1 wrong) estimated as a sample average over training visits. Rows marked static fallback were never visited in offline training; they show -- rather than a misleading 0.00, because the policy seeds those states from the static 2×2 table instead of guessing. Where the learned policy disagrees with the static table, the static answer is shown beside the decision.

Audit Log Integrity

Two independent checks, reported separately on purpose because they defeat two different attackers. Hash chain catches someone who edits a row and does not recompute every following hash. Checkpoint cross-check catches the stronger attacker who does recompute them — the checkpoints live in a different file, HMAC'd with a key no device holds, so a consistently-rewritten in-DB chain still fails to match. Both must pass.
Live data polled from this gateway's /api/* endpoints every 2 s — one real ESP32 + MPU6050 (esp32-vib-001) alongside two simulated scalar devices. SHAP contributions are the fusion meta-learner's per-signal log-odds attribution (direction always correct; magnitude in log-odds, not the 0 to 1 trust scale).
